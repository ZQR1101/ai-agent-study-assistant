# 个性化伴学智能体改造方案

## 1. 文档目标

本文档用于指导现有 AI Study Assistant 从“自由聊天 + 单轮学习工作流”升级为可演示、可持续、可评估的个性化伴学智能体。

改造目标不是复制 DeepTutor，而是借鉴其统一 Agent Runtime、多学习循环、可检查记忆和掌握路径等设计思想，将现有 RAG、ToolRegistry、`/learn` 工作流和 L1/L2/L3 Memory 组合成一个面向赛事的最小可行闭环。

参考项目： [HKUDS/DeepTutor](https://github.com/HKUDS/DeepTutor)

## 2. 当前基线与主要问题

### 2.1 已有能力

- FastAPI 后端和 React/Vite 前端。
- RAG 检索、重排、引用来源和索引重建。
- `ToolRegistry` 工具注册与调用机制。
- `learn` 能力：检索、讲解、总结、出题、建议。
- LangGraph 相关运行时和 Planner 评估脚本。
- L1 原始事件、L2 学习事实、L3 学习画像三层 Memory。

### 2.2 当前断点

1. `/agent` 更接近任务分类器，尚未成为持续管理学习任务的 Agent。
2. `/learn` 是线性流程，每次从主题重新开始，不能依据掌握度决定下一步。
3. Memory 已能记录课程和测验，但没有成为路径规划的硬输入。
4. 测验结果、错误类型和提示过程没有统一的数据模型。
5. 前端主要展示聊天结果，无法证明画像、路径、掌握度发生了变化。

## 3. 目标架构

```text
用户输入/答题行为
        ↓
学习事件采集器
        ↓
学情诊断器 ─────→ Student Profile
        ↓                  ↓
知识点掌握度更新     持续学习路径 Planner
        ↓                  ↓
分级辅导 Tutor ←──── 今日任务与学习循环
        ↓
结果评估与反思
        ↓
L1 事件 → L2 事实 → L3 画像 → 路径再次调整
```

建议新增一个 `伴学运行时`，负责按学习阶段调度已有工具：

```text
diagnose → plan → assign → teach → practice → scaffold → evaluate → reflect
```

每个阶段都输出结构化状态，不只输出自然语言。

## 4. 核心领域模型

### 4.1 学习会话

```python
class StudySession(BaseModel):
    session_id: str
    student_id: str
    goal: str
    subject: str | None = None
    status: Literal["diagnosing", "learning", "paused", "completed"]
    current_node_id: str | None = None
    path_id: str | None = None
    created_at: str
    updated_at: str
```

### 4.2 知识点掌握状态

```python
class MasteryState(BaseModel):
    student_id: str
    concept_id: str
    concept_name: str
    mastery: float = Field(ge=0, le=1)
    confidence: float = Field(ge=0, le=1)
    attempts: int = 0
    correct_attempts: int = 0
    error_patterns: list[str] = []
    last_seen_at: str | None = None
    evidence_event_ids: list[str] = []
```

`mastery` 表示估计掌握度，`confidence` 表示系统对该估计的信心，二者不要混用。

### 4.3 学习路径

```python
class LearningPath(BaseModel):
    path_id: str
    student_id: str
    goal: str
    version: int = 1
    nodes: list["PathNode"]
    current_node_id: str | None = None
    adjustment_reason: str | None = None
    updated_at: str

class PathNode(BaseModel):
    node_id: str
    concept_id: str
    title: str
    prerequisites: list[str] = []
    status: Literal["locked", "available", "in_progress", "mastered", "review"]
    estimated_minutes: int = 15
    mastery_target: float = 0.8
    recommended_actions: list[str] = []
```

### 4.4 诊断结果

```python
class DiagnosisResult(BaseModel):
    diagnosis_id: str
    student_id: str
    goal: str
    questions: list[dict]
    answers: list[dict]
    mastery_snapshot: dict[str, float]
    strengths: list[str]
    gaps: list[str]
    recommended_start_node: str | None = None
    created_at: str
```

### 4.5 分级辅导状态

```python
class ScaffoldState(BaseModel):
    attempt_id: str
    question_id: str
    concept_id: str
    level: int = Field(default=0, ge=0, le=5)
    student_work: str
    detected_error: str | None = None
    prompts_used: list[str] = []
    resolved: bool = False
```

## 5. 四条核心工作流

### 5.1 首次诊断流程

1. 学生输入目标，例如“我想掌握二次函数”。
2. Agent 提取目标、学科、时间和已有基础。
3. 从知识库或内置题库选取 3～5 道覆盖不同难度的诊断题。
4. 学生作答后，记录答案、耗时、置信度和错误类型。
5. 计算每个知识点的初始掌握度。
6. 生成画像和第一版学习路径。
7. 前端展示“诊断结论 + 推荐起点 + 诊断依据”。

### 5.2 路径规划流程

路径 Planner 的输入必须包括：

- 学习目标；
- 知识点及前置关系；
- 当前掌握度；
- 最近错误；
- 可用学习资源；
- 每日可用时间；
- 上一次路径调整原因。

Planner 输出结构化 JSON，不直接输出页面文案。路径调整触发条件建议为：

- 某知识点掌握度低于 0.6；
- 同类错误连续出现两次；
- 连续两次提示后仍无法独立完成；
- 掌握度达到 0.8 且完成变式题；
- 学生主动修改学习目标或时间。

### 5.3 今日任务流程

每日任务控制在 3～5 个步骤：

```text
复习前置知识 → 学习新概念 → 示例 → 独立练习 → 小结/反思
```

任务必须绑定路径节点和知识点，完成后产生 `task_completed` 事件。

### 5.4 错题脚手架流程

```text
学生提交答案
  ↓
判断正确性与错误类型
  ↓
追问：你是如何得到这个结果的？
  ↓
一级提示：提醒相关概念
  ↓
二级提示：缩小解题范围
  ↓
三级提示：给出相似例题
  ↓
局部提示：展示下一步，而非完整答案
  ↓
学生重做
  ↓
评估掌握度并更新路径
```

如果学生明确表示“直接告诉我答案”，也应先给出思路骨架，再根据配置决定是否展示完整解析。

## 6. Memory Engine 改造

### 6.1 扩展 L1 事件类型

在现有事件基础上增加：

```python
L1EventType = Literal[
    "run_completed", "lesson_completed", "quiz_result",
    "topic_discussed", "preference_expressed",
    "diagnosis_completed", "task_assigned", "task_completed",
    "answer_submitted", "scaffold_requested", "reflection_completed",
    "path_updated",
]
```

事件数据至少包含 `student_id`、`session_id`、`concept_id`、`source` 和可追溯的原始证据。

### 6.2 扩展 L2 分类

增加：

- `mastery_evidence`：掌握度证据；
- `error_pattern`：错误模式；
- `path_decision`：路径调整事实；
- `scaffold_preference`：脚手架偏好；
- `engagement`：参与度和节奏。

### 6.3 画像输出

`get_context_for_llm()` 不应只返回文本，还应提供结构化上下文：

```python
{
  "profile": {...},
  "mastery": [...],
  "active_path": {...},
  "recent_errors": [...],
  "recent_events": [...],
  "constraints": {"daily_minutes": 30}
}
```

文本格式仅作为 LLM Prompt 适配层，页面和 Planner 使用结构化数据。

## 7. 后端模块改造建议

新增目录：

```text
backend/companionship/
├── models.py              # 会话、画像、掌握度、路径、任务模型
├── runtime.py             # 伴学状态机
├── diagnosis.py           # 诊断题生成与评分
├── mastery.py             # 掌握度更新
├── path_planner.py        # 路径生成和调整
├── scaffold_tutor.py      # 分级提示与追问
├── reflection.py          # 学习结果反思
└── repository.py          # JSON/SQLite 持久化
```

保留并复用：

- `backend/rag_service.py`：知识和题目检索；
- `backend/tool_registry.py`：工具调度；
- `backend/capabilities/learn.py`：讲解、总结、出题能力；
- `backend/memory/`：事件、事实和画像存储；
- `backend/langgraph_runtime.py`：需要稳定状态恢复时使用。

不建议第一阶段重写现有 `/agent`，而是新增伴学 API，待稳定后再将 `/agent` 路由到伴学运行时。

## 8. API 设计

### 创建伴学会话

`POST /api/companion/sessions`

```json
{
  "student_id": "demo_001",
  "goal": "掌握二次函数",
  "daily_minutes": 30,
  "mode": "guided"
}
```

### 启动诊断

`POST /api/companion/sessions/{session_id}/diagnosis`

### 提交诊断答案

`POST /api/companion/diagnosis/{diagnosis_id}/answers`

### 获取当前画像

`GET /api/companion/students/{student_id}/profile`

### 获取当前路径

`GET /api/companion/sessions/{session_id}/path`

### 获取今日任务

`GET /api/companion/sessions/{session_id}/today`

### 提交练习答案

`POST /api/companion/tasks/{task_id}/attempts`

### 获取下一步提示

`POST /api/companion/attempts/{attempt_id}/scaffold`

### 完成反思

`POST /api/companion/sessions/{session_id}/reflection`

所有响应建议同时返回：`data`、`next_action`、`state_version`、`trace_id`。这样前端可以展示 Agent 的状态变化，调试时也能追踪一次学习循环。

## 9. 前端赛事展示页

建议新增一个“我的伴学”主入口，包含以下区域：

### 学情总览

- 当前学习目标；
- 总体掌握度；
- 已掌握、学习中、待巩固知识点数量；
- 最近一次诊断时间；
- 最近错误类型。

### 当前路径

使用节点卡片展示：已完成、进行中、待学习、需要复习。每个节点显示掌握度、前置知识和推荐原因。

### 今日任务

每个任务显示预计用时、任务类型、关联知识点和完成状态。

### 掌握度变化

使用折线图或条形图展示诊断前、练习后和复习后的变化。演示数据必须来自真实事件，而不是静态装饰。

### Agent 决策依据

展示类似文案：

> 因为你在“顶点式”题目中连续两次出现符号错误，系统将该知识点加入今日复习，并先安排一个基础变式题。

这是证明 Agent 具备记忆、推理和规划能力的关键页面。

## 10. Planner 输出约束

Planner 必须使用 Pydantic/JSON Schema 校验，禁止直接信任自由文本输出。至少校验：

- 所有节点引用的知识点存在；
- 前置节点不能依赖后置节点；
- 当前节点必须处于 `available` 或 `in_progress`；
- 掌握度和阈值在 0～1；
- 每日任务数量和总时长受限制；
- 每次调整必须包含 `reason` 和证据事件 ID。

## 11. 掌握度更新策略

第一阶段可以采用可解释的规则模型，不必一开始引入复杂知识追踪模型：

```text
答对基础题       +0.10
答对变式题       +0.15
独立完成重做     +0.12
使用一级提示后答对 +0.05
使用三级提示后答对 +0.02
答错            -0.08
同类错误重复     -0.12
```

更新后截断到 `[0, 1]`，并保留每次更新的证据。后续再替换为 BKT、IRT 或其他知识追踪算法时，不影响前端和 API。

## 12. 实施顺序

### 阶段一：数据和读取链路

- 新增伴学领域模型；
- 扩展 L1/L2 事件类型；
- 增加画像、掌握度、路径读取 API；
- 编写模型和序列化测试。

验收：完成一次诊断后，可以通过 API 读取画像和掌握度。

### 阶段二：诊断和路径

- 实现诊断题生成；
- 实现规则评分；
- 实现首版路径 Planner；
- 将路径写入 Memory 和持久化存储。

验收：同一目标下，两个不同掌握度的学生得到不同起始节点或任务。

### 阶段三：伴学运行时

- 实现 `diagnose → plan → task → evaluate` 主循环；
- 接入现有 RAG 和学习工具；
- 每个阶段输出结构化 trace。

验收：完成一次任务后，路径版本号递增，调整原因可追溯。

### 阶段四：脚手架辅导

- 实现错误分类；
- 实现五级提示策略；
- 增加追问、重做和掌握度更新。

验收：演示中 Agent 不直接公布答案，而是通过至少两次干预帮助学生完成重做。

### 阶段五：赛事前端和演示

- 学情总览；
- 当前路径；
- 今日任务；
- 掌握度变化；
- 诊断结果；
- Agent 决策依据。

验收：不打开日志和代码，仅通过页面即可解释一次完整学习闭环。

## 13. 测试与评估

### 自动化测试

- 画像和掌握度模型校验；
- 事件追加和引用完整性；
- 路径 DAG 无环校验；
- Planner 非法 JSON 修复；
- 脚手架等级递进；
- 任务完成后的路径更新；
- 多会话 Memory 隔离。

### 赛事演示指标

- 诊断结果是否能解释；
- 路径是否因学生差异而不同；
- 错题后是否产生分级干预；
- 重新答题后掌握度是否变化；
- 下一次任务是否使用了历史记忆；
- 页面是否展示完整证据链。

### 建议增加的评估字段

```json
{
  "diagnosis_accuracy": 0.0,
  "path_relevance": 0.0,
  "scaffold_helpfulness": 0.0,
  "answer_leakage": false,
  "memory_used": true,
  "path_adjusted": true
}
```

## 14. 演示脚本

以“二次函数”为例：

1. 学生输入学习目标和每天可用时间。
2. Agent 发起 3 道诊断题。
3. 系统识别“函数概念较好、顶点式薄弱”。
4. 页面展示画像和推荐路径。
5. Agent 分配“顶点式基础任务”。
6. 学生第一次答错，Agent 追问解题思路。
7. 学生再次答错，Agent 给出类比题和局部提示。
8. 学生独立完成重做。
9. 系统更新掌握度和错误记录。
10. 路径自动将“顶点式”标记为复习完成，并安排下一知识点。
11. 页面展示掌握度变化和路径调整原因。

## 15. 非目标与风险控制

第一阶段不做：

- 多学科全量知识图谱；
- 多 Agent 复杂协作；
- 视频、语音和完整家校系统；
- 复杂商业账户体系；
- 无法验证效果的炫技功能。

优先保证一条学科、一个完整目标和一套真实演示数据跑通。重点是“状态持续更新、路径确实改变、辅导过程可见”。

## 16. 最终交付清单

- 伴学运行时和状态机；
- 学情诊断数据模型；
- 掌握度更新模块；
- 可持续学习路径 Planner；
- 分级脚手架 Tutor；
- Memory Engine 接入画像和路径；
- 五个赛事展示页面；
- API 文档和架构图；
- 自动化测试与演示数据；
- 3～5 分钟赛事演示脚本；
- 计划书中的技术架构、创新点和落地价值说明。

## 17. 改造优先级

```text
P0 诊断数据模型、掌握度、路径、错题脚手架
P1 Memory 接入路径调整、伴学状态机、赛事展示页
P2 解释性、主动提醒、激励机制、评估指标
P3 多模态、复杂知识图谱、多 Agent 协作
```

最终判断：现有项目最适合走“轻量但完整”的伴学闭环路线。只要 P0 和 P1 做扎实，就能明显区别于普通聊天机器人，并直接覆盖赛题中的学情诊断、路径规划、实时干预、记忆反思四项核心能力。
